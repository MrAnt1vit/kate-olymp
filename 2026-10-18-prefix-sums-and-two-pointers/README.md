## 1. Что такое префиксная сумма

`p[k]` — сумма **первых `k`** элементов массива `a`. Поэтому `p[0] = 0`, `p[1] = a[0]`, а `p[k+1] = p[k] + a[k]`. Для отрезка с границами `l` и `r` включительно:

```text
сумма a[l] + … + a[r] = p[r+1] − p[l].
```

`p[r+1]` содержит элементы до `a[r]` включительно, а `p[l]` отнимает всё перед `a[l]`. Эта одна формула связывает первые две задачи занятия. На доске она была записана как `pref[j+1] - pref[i]`.

## 2. Самый длинный отрезок с суммой, кратной трём

Нужно выбрать непустой отрезок максимальной длины, для которого `(p[r+1] - p[l]) % 3 == 0`. Разность делится на 3 тогда и только тогда, когда у двух префиксов **одинаковый остаток** при делении на 3:

```text
p[r+1] % 3 == p[l] % 3.
```

На занятии это сначала объяснялось через десять: если разность `x−y` делится на 10, у `x` и `y` одинаковые последние цифры. Затем преподаватель предложил случай `x = 3k+2`: чтобы `x−y` делилось на 3, вычитаемое `y` тоже должно иметь остаток `2`. Здесь нужна **разность** остатков, равная нулю; сложение остатков было бы другой задачей.

### Пример с доски

На схеме зафиксирована **правая граница массива `j=10`**, а сумма отрезка записана как `pref[j+1]−pref[i]`. У `pref[11]` остаток `1`; у левых префиксов с индексами **`i=1, 4, 5, 7`** тот же остаток. Числа элементов массива на доске **не задавались**. Для каждого кандидата длина отрезка `[i,j]` равна `j−i+1`:

| `i` с доски | Отрезок при `j=10` | Длина |
| ---: | --- | ---: |
| 1 | `[1,10]` | **10** |
| 4 | `[4,10]` | 7 |
| 5 | `[5,10]` | 6 |
| 7 | `[7,10]` | 4 |

Поэтому преподаватель и Катя выбрали `i=1`: среди префиксов с нужным остатком он расположен левее всех. Важно не спутать `j=10` с индексом правого **префикса**: здесь это именно индекс последнего элемента, а правый префикс — `pref[11]`.

На доске предложен ещё один взгляд: для каждого остатка найти самый **ранний** и самый **поздний** индекс префикса. Это всего шесть крайних индексов; сравниваем три разности «поздний минус ранний». Для однопроходной реализации достаточно хранить первые появления каждого остатка. При очередном `p[k]` с остатком `t` кандидат на длину равен `k - first[t]`; если `first[t]` ещё не задан, записываем `k`.

Почему это работает: для фиксированного правого `k` более ранний подходящий левый индекс всегда даёт более длинный отрезок. Поздние появления того же остатка не нужно сохранять вместо раннего. `first[0] = 0` задаётся до просмотра массива, ведь `p[0] = 0`; иначе потеряем отрезки от первого элемента. Если суммы могут быть отрицательными, в C++ нормализуем остаток: `((p[k] % 3) + 3) % 3`. Время — `O(n)`, память для трёх индексов — `O(1)`. **Полную программу на занятии не писали**: это осталось самостоятельной задачей. [Решение по разобранной идее](examples/divisible_by_three.cpp) добавлено после занятия с условным учебным форматом ввода.

## 3. «Сумма чисел в массиве»: максимальная сумма отрезка

В задаче, открытой на «Сириусе», дано `n ≤ 100000` чисел с `|a[i]| ≤ 30000`. Требуется **непустой** непрерывный отрезок с наибольшей суммой. При равных суммах выбираем **наименьший правый индекс `j`**, а если он одинаковый — **наибольший левый индекс `i`**. В ответе индексы с единицы.

Формат входа: сначала `n`, затем `n` чисел массива. Вывод: два индекса `i j`.

**Первый пример из условия** (числа были показаны по одному в строке; переносы здесь сокращены):

```text
Ввод                  Вывод
5                     2 3
-1 2 3 -2 2
```

Отрезок с индексами `2..3` по условию содержит `2, 3`, сумма `5`. Если продлить его до пятого элемента, получится `2+3−2+2=5` — та же сумма, но правый индекс `5` больше `3`. Поэтому выводится `2 3`.

**Второй пример из условия**, который преподаватель затем запускал и исправлял в CLion:

```text
Ввод                  Вывод
7                     3 7
2 -2 3 -1 5 -2 7
```

Сумма всего массива `2−2+3−1+5−2+7=12`. Сумма от третьего до седьмого элемента тоже `3−1+5−2+7=12`. Правый индекс у них одинаков (`7`), а из левых индексов по условию нужен **максимальный**, то есть `3`.

### Как из формулы получить линейный алгоритм

Если правый конец `j` уже известен, сумма отрезка равна `p[j+1] - p[i]`. `p[j+1]` фиксирован, значит для максимума нужно вычесть **наименьший среди `p[0] … p[j]`**. Обозначим индекс такого префикса `imin`. В показанном коде лучший ответ хранится как `ibest, jbest`.

Для каждой позиции `j` делаем следующее:

1. Читаем `a[j]`, получаем `p[j+1] = p[j] + a[j]`.
2. Сравниваем `p[j]` с текущим минимальным префиксом. При равенстве обновляем `imin = j`: более поздний левый индекс нужен по правилу задачи.
3. Проверяем сумму кандидата `p[j+1] - p[imin]`. При **строгом** улучшении заменяем `ibest, jbest`; при равной сумме оставляем прежний ответ, потому что его правый конец встретился раньше.

На первый взгляд странно, что `p[j]` проверяется после вычисления `p[j+1]`. Но `p[j]` — последний **допустимый** левый префикс для отрезка, заканчивающегося в `j`. Включать в минимум `p[j+1]` пока нельзя: получилось бы пустое окно `[j+1, j]`. Если сначала считать кандидата, а потом внести `p[j]` в минимум, случай из одного элемента `a[j]` можно пропустить.

В CLion преподаватель свёл чтение, построение префиксов, выбор минимума и обновление ответа в **один цикл**. Существенные строки показанного решения:

```cpp
p[j + 1] = p[j] + a[j];
if (p[j] <= p[imin]) imin = j;
if (p[j + 1] - p[imin] > p[jbest + 1] - p[ibest]) {
    jbest = j;
    ibest = imin;
}
```

При запуске второго примера примерно на **32:55** программа сначала вывела `1 8`: `jbest` ошибочно присваивалось `j+1`, а при выводе единица прибавлялась ещё раз. После исправления `jbest=j` получилось `1 7`. Затем преподаватель вернул условие `p[j] <= p[imin]` вместо строгого `<`, и результат стал `3 7`. Это два **разных** исправления: индексация правого конца и выбор более позднего левого конца при равной сумме префиксов.

[Рабочая версия показанного алгоритма](examples/max_subarray.cpp) сохраняет обозначения `p`, `imin`, `ibest`, `jbest` и порядок действий. В ней есть два технических дополнения для общего случая: префиксы хранятся в `long long` (`100000 × 30000 = 3·10⁹` не помещается в обычный `int`), а лучшая сумма изначально считается отсутствующей, чтобы корректно работал массив из отрицательных чисел. Это не буквальная копия промежуточного кода на экране.

Для проверки из папки занятия: `g++ -std=c++17 -O2 examples/max_subarray.cpp -o max_subarray`, затем запустите `./max_subarray` и введите один из двух приведённых выше блоков «Ввод».

### Проследим второй пример

Для чисел, показанных в условии, префиксы равны `0, 2, 0, 3, 2, 7, 5, 12`. Ниже **наша проверка по шагам показанного цикла**, а не отдельная таблица с экрана. `j` и `imin` здесь считаются с нуля; ответ в последнем столбце уже с единицы.

| `j` | `a[j]` | `p[j+1]` | `imin` после сравнения с `p[j]` | Кандидат `p[j+1]-p[imin]` | Лучший ответ |
| ---: | ---: | ---: | ---: | ---: | --- |
| 0 | 2 | 2 | 0 | 2 | `1 1` |
| 1 | −2 | 0 | 0 | 0 | `1 1` |
| 2 | 3 | 3 | **2** | 3 | `3 3` |
| 3 | −1 | 2 | 2 | 2 | `3 3` |
| 4 | 5 | 7 | 2 | 7 | `3 5` |
| 5 | −2 | 5 | 2 | 5 | `3 5` |
| 6 | 7 | 12 | 2 | 12 | **`3 7`** |

Ключевой момент — `j=2`: `p[2]=0` равно уже встреченному `p[0]=0`, и условие `<=` переводит `imin` с `0` на `2`. Если оставить строгий `<`, в конце получится показанный при отладке неверный ответ `1 7`.

Сложность: `O(n)` времени и `O(n)` памяти для показанного массива префиксов.

## 4. Два указателя: отрезок с заданной суммой

Дальше рассматривали массив **неотрицательных** чисел и искали отрезок с суммой `x`. Пусть текущий отрезок `[l, r]` имеет сумму `ans`. Если `ans < x`, сдвиг `r` вправо и добавление нового числа может увеличить сумму. Если `ans > x`, сдвиг `l` вправо и вычитание покинувшего элемента может уменьшить сумму. При `ans == x` выводим найденные границы. В коде на экране границы внутренних индексов переводились в ответ как `l+1` и `r+1`.

На Miro была нарисована граница для фиксированного `l`: слева от неё суммы меньше `x`, справа — больше `x`. Когда `l` растёт, сумма при прежнем `r` не увеличивается, так что правой границе незачем возвращаться влево. Оба указателя идут только вперёд. Хотя при записи с `for` и вложенным `while` видно два цикла, каждый указатель сдвинется максимум `n` раз: суммарно `O(n)` времени.

### Числа, с которыми работали в отладчике

Пример преподаватель **набрал в CLion около 52:15** для задачи из раздела теории:

```text
Ввод                  Вывод после исправления программы
6 10                  3 5
4 2 6 1 3 5
```

В ролике левая и правая границы хранятся с нуля, а выводятся с единицы. Сначала преподаватель прошёл этот ввод через вариант с внешним `for`, затем запустил на нём вариант `while (true)`. Вот проговорённый им ход окна:

| Шаг | `l` | `r` | Окно | `ans` | Действие |
| ---: | ---: | ---: | --- | ---: | --- |
| 1 | 0 | 0 | `4` | 4 | Мало: добавить справа `2`. |
| 2 | 0 | 1 | `4 2` | 6 | Мало: добавить `6`. |
| 3 | 0 | 2 | `4 2 6` | 12 | Много: убрать слева `4`. |
| 4 | 1 | 2 | `2 6` | 8 | Мало: добавить `1`. |
| 5 | 1 | 3 | `2 6 1` | 9 | Мало: добавить `3`. |
| 6 | 1 | 4 | `2 6 1 3` | 12 | Много: убрать `2`. |
| 7 | 2 | 4 | `6 1 3` | 10 | Найден отрезок, ответ **`3 5`**. |

В записи были два способа оформить эту идею. Сначала преподаватель написал вариант с `while (true)`, но ошибочно поставил в ветку `ans < x` удаление слева. Первый запуск вывел `-1`; он сначала исправил место считывания входа, но результат всё ещё не получился. Примерно на **55:25** в отладчике обнаружились перепутанные направления: исправление на **`ans > x` → сдвинуть `l`**, **`ans < x` → сдвинуть `r`** привело к ответу `3 5`.

Основная часть **исправленного кода с экрана** (массив `a`, `n` и `x` уже считаны):

```cpp
int l = 0, r = 0;
int ans = a[0];
while (true) {
    if (ans == x) {
        cout << l + 1 << ' ' << r + 1;
        break;
    }
    if (ans > x) {
        ans -= a[l];
        l++;
        if (l == n) break;
    } else {
        r++;
        if (r == n) break;
        ans += a[r];
    }
}
if (ans != x) cout << -1;
```

[Запускаемая версия с `while`](examples/segment_sum_while.cpp) сохраняет эту структуру; в ней также обработан случай опустевшего окна, чтобы программа работала при нулях.

Отдельно преподаватель переписал алгоритм так, чтобы внешний `for` явно перебирал **левую** границу `l`, а внутренний `while` только продвигал `r`. При переходе к следующему `l` из суммы вычитается старый `a[l-1]`; `r` не обнуляется.

Вот основные строки **второго варианта с экрана** после чтения массива (`r=0`, `ans=a[0]`); это фрагмент хода решения, а не отдельная готовая программа:

```cpp
for (int l = 0; l < n; l++) {
    if (l > 0) ans -= a[l - 1];
    while (ans < x && r < n - 1) {
        r++;
        ans += a[r];
    }
    if (ans == x) {
        cout << l + 1 << ' ' << r + 1;
        break;
    }
}
```

[Запускаемая версия с внешним `for`](examples/segment_sum_for.cpp) отличается только вводом, завершением и проверкой, что после сдвига `l` окно не стало пустым. На показанном входе оба варианта печатают `3 5`.

В обоих фрагментах `r` перед обращением к `a[r]` проверяется на конец массива. Вариант с `for` останавливает расширение при `r=n−1`, а вариант с `while` допускает `r=n` лишь как сигнал остановки, **не читая `a[n]`**. В этом и был важный разговор о границах на занятии.

Проверка `ans == x` должна относиться к **непустому** окну. Если допустимы нули и `x=0`, особенно внимательно проверьте этот случай: после удаления элемента окно может опустеть. При отрицательных элементах объяснение монотонности уже неверно: добавление справа может уменьшить сумму. Тогда нужен другой метод, например поиск нужной разности префиксов.

## 5. «Город Че»: пары памятников

В последней задаче даны `n ≤ 300000` памятников с **возрастающими** координатами `a[0] < … < a[n−1]` и расстояние `R`. Нужно подсчитать пары различных памятников `i < j`, для которых **`a[j] − a[i] > R`**. Равенство `R` не подходит.

На входе сначала стоят `n R`, затем `n` координат. На выходе — одно число пар.

**Пример из условия на экране** (около 58-й минуты):

```text
Ввод                  Вывод
4 4                   2
1 3 5 8
```

Объяснение в условии называет памятники по номерам: подходят **1-й и 4-й** (`1` и `8`), **2-й и 4-й** (`3` и `8`). Расстояния `7` и `5` строго больше `R=4`. Всего `4·3/2=6` пар; оставшиеся четыре имеют расстояние не больше 4.

Преподаватель сначала считал **близкие** пары и собирался вычесть их из всех пар. Для текущего `l` указатель `r` — первый индекс, у которого `a[r] − a[l] > R`; если такого памятника нет, `r=n`. Тогда `r−l−1` — число правых памятников на расстоянии `≤R`: индексы от `l+1` до `r−1` включительно.

Преподаватель запустил первый вариант `while`, и программа напечатала **3 вместо 2**. В отладчике он последовательно увидел такие состояния:

| `l` | `r` | Разность | Что успел посчитать первый вариант |
| ---: | ---: | ---: | --- |
| 0 (`1`) | 1 (`3`), затем 2 (`5`) | 2, затем **4** | Обе пары ещё близкие, потому что `4 ≤ R`. |
| 0 (`1`) | 3 (`8`) | 7 | Добавил `3−0−1=2`: пары `(1,3)` и `(1,5)`. |
| 1 (`3`) | 3 (`8`) | 5 | Добавил `3−1−1=1`: пара `(3,5)`. |
| 2 (`5`) | 3 (`8`) | 3 | Правый указатель уже на последнем элементе; ошибочный выход из цикла **не добавил** `(5,8)`. |

Так набралось лишь **3 близкие пары**, и выражение `6−3` напечатало ошибочное **3**. На записи преподаватель именно здесь обнаружил проблему: последние левые границы ещё нужно обработать, даже если правый указатель дошёл до конца. В качестве устного продолжения он произнёс гипотетический хвост **`5, 8, 9`**: тогда были бы близкими пары `(5,8)`, `(5,9)` и `(8,9)`; один преждевременный выход потерял бы их все. Это не отдельный вход задачи, а иллюстрация ошибки границы.

Ниже — **наша развёртка того же входа после исправления идеи**, чтобы можно было самостоятельно досчитать ответ. Такой таблицы на экране не было:

| Левый памятник | Первый `r` с расстоянием `>4` | Близкие справа | Их число `r−l−1` |
| --- | --- | --- | ---: |
| `1` (`l=0`) | `8` (`r=3`) | `3, 5` | 2 |
| `3` (`l=1`) | `8` (`r=3`) | `5` | 1 |
| `5` (`l=2`) | нет (`r=4`) | `8` | 1 |
| `8` (`l=3`) | нет (`r=4`) | нет | 0 |

Получаем `2+1+1+0=4` близкие пары и `6−4=2` далёкие. После обсуждения преждевременного выхода преподаватель начал переделывать подсчёт через внешний `for`. Смысл строк, которые он записал к концу занятия: `r` доходит до **`n`**, при `r<n` можно обновлять `diff`, после продвижения правой границы к ответу за очередное `l` прибавляется **`r-l-1`**. Благодаря внешнему `for` учитываются все `l`, даже когда `r=n`. В редакторе остался рабочий черновик с поправками на `diff`; завершённого и проверенного решения этой задачи на записи **нет**.

Вот **фрагмент верхнего цикла с экрана около 75:50**; после него в редакторе оставался и старый вариант `while`, поэтому весь файл в таком состоянии не был готов к отправке в проверяющую систему:

```cpp
int r = 0;
int diff = 0;
int ans = 0;
for (int l = 0; l < n; l++) {
    if (l != 0) diff -= a[l] - a[l - 1];
    while (diff <= x && r < n) {
        r++;
        if (r != n) {
            diff += a[r] - a[r - 1];
        }
    }
    ans += r - l - 1;
}
```

Здесь `x` — расстояние из входа, `diff` — разность координат при текущих указателях, а `ans` накапливает **близкие** пары, которые затем надо вычесть из `n(n−1)/2`. Если дописывать программу для всех ограничений, счётчик пар должен иметь тип `long long` вместо показанного `int`.

[Законченная для практики программа](examples/monuments.cpp) повторяет этот внешний `for`, считает близкие пары и вычитает их из всех. В ней `long long` применён к количеству пар. Она **написана после занятия** по последнему наброску, потому что исходный экранный файл остался незавершённым.

Для самостоятельного дописывания держите инвариант: перед подсчётом для очередного `l` указатель `r` должен быть первым индексом **после** всех координат на расстоянии `≤R`; `r` никогда не уменьшается. После `r=n` обращаться к `a[r]` нельзя, но вклад `r−l−1` для следующих `l` считать всё равно нужно. Ответ и общее число пар храните в `long long`: при `n=300000` всего `44 999 850 000` пар.

## Проверка понимания

1. Почему в первом примере задачи о максимальной сумме ответ заканчивается на `3`, хотя отрезок до `5` имеет такую же сумму?
2. Почему во втором примере ответ начинается с `3`, хотя отрезок от `1` до `7` имеет ту же сумму?
3. Какой переход делаем для окна `4 2 6`, если `x=10`? Что будет после него?
4. Почему в задаче о памятниках после `r=n` внешний цикл должен продолжаться?

<details><summary>Ответы</summary>

1. По условию выбирается наименьший правый индекс среди максимумов: `3 < 5`.
2. Правый конец одинаковый (`7`), поэтому берём наибольший левый индекс: `3 > 1`. В коде это обеспечивается обновлением `imin` при равных минимальных префиксах.
3. Сумма `12 > 10`, значит убираем слева `4`: окно `2 6`, сумма `8`. Затем можно расширяться вправо.
4. Для более поздних левых памятников пары ещё существуют, хотя справа уже нет координат с расстоянием `>R`: нужно досчитать близкие пары и только после этого вычесть их из общего числа.

</details>
